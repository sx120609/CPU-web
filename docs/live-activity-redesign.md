# 课程实时活动实现方案

整理日期：2026-09-22。状态：实现设计，尚未实现。2026-09-22 更新：补齐逐节选课、课程身份、分节状态、预约恢复、作息变更及验收规则；iOS 26+ 固定采用未来 7 天本地预约，iOS 18–25 采用 APNs 远程启动。

本文汇总当前讨论结论。现有实现说明见 [apns.md](apns.md)，本文不代表现有功能已经完成改造。不调整 UI 视觉设计，仅调整设置能力、课程时间线及实时活动生命周期。

## 1. 目标与已确定的设计

- 课前提前量支持 15 分钟、30 分钟、1 小时。
- 到提醒时间显示距上课倒计时；上课后切换为距下课倒计时。
- 连堂课支持分节计时和整堂计时；分节模式在课间显示距下一小节上课的倒计时。
- 本次课程最后一小节结束后关闭活动，不关闭功能总开关。
- 用户手动移除活动后，下次打开 App（冷启动或从后台回到前台）自动恢复仍符合启动条件的课程；关闭设置总开关则结束活动、取消全部预约并撤销远程计划，打开 App 不会自动开启总开关。
- 按课程最终下课节次分频道，批量更新和结束，不采用全量逐活动结束推送。
- 固定频道按最终节次跨日复用，不按日期新建。
- iOS 26+ 每次配置未来 7 天的本地预约，不使用远程启动兜底；iOS 18–25 使用 APNs 远程启动。
- 下一门课不得在上一门课结束前启动；每次修改提前量都重新计算并配置未启动的计划。
- 客户端上传本次课程最后节次，由服务端依据已同步的学校作息表匹配频道；远程启动路径不要求客户端选择或上传 APNs channel ID。

一次活动对应一门课的一次上课。两小节连堂课保持同一活动，不在课间结束再创建；相邻的不同课程不自动合并。

导入课表后，同一实际日期的每个节次只能保留一门课。存在冲突时，用户必须逐节选择后才能生成有效计划，不由实时活动调度器自动决定课程优先级。例如 A 占第 1–3 节、B 占第 2–4 节，用户可在第 2 节选 A、第 3 节选 B，最终得到 A 第 1–2 节、B 第 3–4 节。活动按选择后的实际连续课程段生成；同一课程被另一门课隔开的片段分别生成活动，各自使用实际最后节次的结束频道。未解决的冲突不能直接进入启动计划。

选择结果作用于明确的实际日期及节次；批量应用到多周时，先展开对应日期再保存选择。按来源课程身份合并连续节次，不能仅凭课程名称相同就合并。编辑产生未解决冲突时，撤销受影响课程的未启动计划，其他无冲突课程继续运行；解决后重新展开并同步。首版要求同一份有效作息表的节次按时间有序且互不重叠，不满足时拒绝发布作息。

## 2. 课程时间线

以 08:00–08:45、08:55–09:40 两小节连堂课、提前 15 分钟为例：

| 时间 | 分节计时 | 整堂计时 |
| --- | --- | --- |
| 07:45 | 距上课 15 分钟 | 距上课 15 分钟 |
| 08:00 | 第一小节，距下课 45 分钟 | 距最终下课 100 分钟 |
| 08:45 | 课间，距上课 10 分钟 | 距最终下课 55 分钟 |
| 08:55 | 第二小节，距下课 45 分钟 | 距最终下课 45 分钟 |
| 09:40 | 结束并收起 | 结束并收起 |

倒计时使用绝对时间，由系统绘制，不逐秒请求服务器。广播只在上课、下课等阶段边界触发刷新；Widget 根据本地课表、当前活动的课程标识及用户设置解析显示状态。

### 2.1 共享时间线模型

App 与 Widget 共用纯函数 `resolveTimeline(occurrence, mode, now)`。每个实例保存有序的 `segments: [{period, startAt, endAt}]`，整门课的开始、结束分别取第一节开始及最后一节结束；课间不伪装成上课小节。所有时间存绝对时间，`dateKey` 及节次解释使用作息表明确提供的学校时区，不跟随手机所在时区变化。

| 时间条件 | 分节模式 | 整堂模式 | 计时目标 |
| --- | --- | --- | --- |
| `now < first.startAt` | `upcoming` | `upcoming` | 第一节开始 |
| `segment.startAt <= now < segment.endAt` | `inClass` | `inClass` | 分节取当前节结束；整堂取最终结束 |
| `segment.endAt <= now < next.startAt` | `break` | `inClass` | 分节取下一节开始；整堂取最终结束 |
| `now >= last.endAt` | `finished` | `finished` | 不显示继续计时 |

边界统一为左闭右开；没有课间间隔时直接进入下一节。返回值包含阶段、当前小节序号、计时起止及最终结束时间，供现有视觉组件使用。切换分节/整堂模式只更新共享设置及当前活动内容，不改变实例身份、频道和预约时间；默认使用整堂模式。

绝对时间倒计时只保证当前目标的秒数由系统绘制，不保证 SwiftUI 在边界自动重新计算阶段。阶段切换依赖广播触发重新渲染，App 在前台时也主动刷新。渲染时按实际 `now` 求状态，不照搬延迟到达的广播阶段。漏收广播时，倒计时到零后停止，可能暂留旧阶段文字，下一次广播或前台核对时恢复；不承诺断网时自动切换全部小节。

### 2.2 展示快照与推送载荷

- 不可变 Activity attributes 保存 `occurrenceId`、本机账号隔离标识、`dateKey`、作息标识/版本、频道、预约起止及最终结束时间。远程启动和本地预约使用同一结构。
- App Group 按账号及 `occurrenceId` 保存课程名称、教师、教室、`segments`、内容版本和显示设置。先原子保存完整快照，再创建预约或提交远程计划；Widget 只解析当前活动对应的实例，不能搜索“当天最近一门课”替代。
- 广播 content-state 只包含协议版本、作息标识/版本、事件时间、事件类型及公共边界信息，不能携带某个学生的课程身份或覆盖 attributes。所有启动、更新和结束载荷均符合相同的可解码 schema；广播中的空课程信息不能覆盖本地个人快照。
- 课表重载不能提前删除仍被活动引用的实例快照。缺失、损坏或账号不匹配时显示通用“课程信息暂不可用”，只使用 attributes 中可信的最终结束时间，不展示其他账号或其他课程的信息。退出账号清除个人快照并结束本机活动。
- `staleDate` 设置为最终结束时间。结束广播提供可解码的最终状态及立即移除时间；页面若仍被系统保留，展示结束状态。正常送达时在最终下课后收起；离线漏收 `end` 时不保证准点移除，前台恢复负责清理。

## 3. 频道分组与生命周期

服务端按学校作息表，为每个可能的最终下课节次管理频道。逻辑键示例：

```text
production:<作息版本>:end-period-2
production:<作息版本>:end-period-4
sandbox:<作息版本>:end-period-2
```

逻辑键是应用内部标识，真实 APNs channel ID 由 Apple 创建并由服务端保存。如果存在多个校区或作息表，键还需包含对应作息表标识。

课程占第 1–2 节时，订阅第 2 节结束频道；无论分节还是整堂模式，都在第 2 节下课时结束。服务端在相关节次边界向频道发 `update`，在最终节次下课时发 `end`，并提供最终 content-state 和立即移除所需的 `dismissal-date`。同一时间的刷新事件去重，结束优先于同频道的普通更新。

频道具有以下约束：

- APNs 广播频道用于 Live Activities，不是普通通知、静默唤醒或普通桌面小组件的通用订阅通道。
- 广播支持更新、结束，不支持创建实时活动。
- `end` 由系统处理，客户端不能根据个人课表选择忽略。
- `end` 不会删除频道，新的活动仍可订阅相同频道；已结束的活动不能复活。
- `staleDate` 只标记内容过期，不会结束或移除活动。
- 主 App 未运行时，不能依赖 Widget 自行调用结束接口完成收起。

固定频道建议使用 No Message Storage，并设置事件的短有效期，避免旧消息积压。该策略不能保证离线设备收到结束事件，本方案按第 8 节的频道复用决策执行。App 回到前台时应清理已过期活动。

### 3.1 广播事件生成

对最终节次为 `p` 的频道，生成该作息表第 1 至 `p` 节的全部开始、结束边界，同刻去重；`p` 节最终结束只生成 `end`，其他边界生成 `update`。不需要知道订阅者实际从哪一节开始，尚无活动订阅的广播没有个人副作用。按持有有效映射的作息版本逐日生成，不因周末、全校放假标签或服务端没有个人课程计划就跳过，避免漏掉本地调课及 iOS 26 预约。

事件唯一键包含环境、作息标识/版本、最终节次、学校日期、边界时间及事件类型。广播任务有效期为边界后 60 秒，发送时使用原始边界时间作为 APNs `timestamp`；同频道按时间推进，结束提交后不再补发更早的更新。失败只在有效期内重试，不把昨天的结束积压到今天发送。频道继续使用 No Message Storage。

### 3.2 作息版本与频道保留

这里的版本用于新版运行期间的作息调整，不用于兼容旧版 App。作息版本发布后不可原地修改时间，调整生成新版本；频道映射与对应版本的完整节次表一起缓存，禁止新时间表搭配旧频道。

本地映射响应包含 `issuedAt`、`usableUntil` 和 `broadcastUntil`：可创建预约的课程开始时间必须早于 `usableUntil = issuedAt + 7 × 24h`，最终结束不得晚于 `broadcastUntil`，旧缓存不能因再次打开 App 自动延长有效期；服务端保证该批映射的频道广播至少持续到 `broadcastUntil = issuedAt + 8 × 24h`，覆盖窗口末尾课程及最长活动时长。记录每个版本已承诺的最晚 `broadcastUntil`，作息更新后仍履行已发映射的保留期；不再签发旧版本映射。在线获取新映射才可延长覆盖，离线只能补足旧映射允许的范围。

新作息生效后，服务端停止执行受影响旧版本的未提交远程启动计划，标记需要重同步；客户端获取新作息后重建未启动计划，已经启动的活动按第 6.2 节处理。旧版本仍按原时间广播至已承诺期限，并覆盖所有已进入 submitting、submitted 或 submissionUnknown 的远程启动的最终结束时间。超过所有保留期限和事件重试期后才可删除旧频道。频道创建失败时不返回假 ID，记录缺失并重试。

## 4. 启动方式

### 4.1 远程启动：可覆盖长期不打开 App 的使用方式

本项目对 iOS 18–25 采用此路径，iOS 26+ 不安排远程启动：

1. 用户登录、加载课表后，客户端取得 push-to-start token，上传设备配置和课程计划。
2. 服务端依据日期、节次、学校时区及提前量先计算理想提醒时间，再按第 4.3 节规则将 `fireAt` 推迟至上一门课结束之后或同一时刻。
3. 到提醒时间，服务端向设备的 push-to-start token 发送 `event: start`，在 `input-push-channel` 中填写最终下课节次对应的频道 ID。
4. iOS 创建活动并订阅频道，不要求用户打开 App。
5. 后续状态更新和结束均通过频道广播完成，无需逐活动更新 token 回传链路。

APNs 不替服务端预约未来发送；请求中的 `timestamp` 是事件时间，不是未来执行时间。服务端必须保持调度运行。首次注册、权限、token 有效性、计划同步及网络是必要条件；APNs 接受请求不等于设备已经显示，不能承诺百分之百准点。

### 4.2 iOS 26+：一次配置未来 7 天的本地预约

固定采用系统预约启动，不使用 APNs 远程启动或混合兜底。创建预约时同时指定计算好的启动时间及最终下课节次对应的频道：

```swift
pushType: .channel(channelID),
start: reservation.start
```

每次配置以当前时刻 `now` 为基准，筛选 `course.end > now` 且 `course.start < now + 7 × 24h` 的课程，覆盖未来连续 168 小时内开始的课程，以及当前尚未结束的课程。按时间顺序计算并尝试预约整个窗口，不再限制为今天、明天或未来 48 小时。

本地预约路径由服务端提供固定频道 ID 与节次映射。客户端根据课程最后节次匹配，同一节次跨日共用频道，不要求每天刷新日期频道映射。系统到点启动，无需 App 保持前台。

配置规则：

- 每次启动 App（冷启动）以及从后台回到前台时，都必须触发滚动预约：以本次当前时间为起点，将预约目标向后延伸至 `now + 7 × 24h`，不能因为上次已预约过就跳过。
- 使用已登录账号的有效课表和频道缓存先核对计划；联网同步得到新课表或作息后再次核对。缺少必要数据时先完成加载，再执行预约。
- 每次滚动核对补充新增窗口内的课程及之前申请失败的缺失预约，撤销已失效的预约；已有且时间、频道、课程身份均未变化的预约原则上保留，不重复创建；额度不足时按下述近期优先规则让位。当前仍有效的 active 活动保持不变。
- 首次登录、课表或作息变化时同样触发上述核对。
- 用户每次修改提前量，按第 6 节取消并重建未启动预约。
- 保留当前已经启动且仍有效的活动，不因窗口滚动而重建。
- 本次更新不兼容旧版客户端、接口或频道协议；切换时清理旧待启动计划及本机旧预约，避免遗留任务重复创建，不设计旧版并行运行路径。
- 7 天是每次启动或回到前台时重新计算的滚动目标范围。例如周一 09:00 启动后覆盖至下周一 09:00，周二 12:00 再启动则向后补充至下周二 12:00。连续不打开 App 时，不承诺系统会自动补充第 8 天及之后的课程；不依赖不确定的后台刷新保证续约。
- 预约计入系统活动数量限额。按时间从近到远申请，记录实际成功覆盖范围和失败；限额不足时不能声称 7 天已全部预约成功，也不自动改用远程启动。

一次核对以账号、课表版本、设置版本和作息版本组成配置代次，全程串行执行；每个异步返回后检查代次，过时任务不得继续创建。单门课数据错误可记录后继续其他课程；遇到系统数量限额时先按下述近期优先规则尝试有限替换；无可替换预约或替换后仍受限则停止本轮新增，避免连续无效申请。App 保持前台时在活动结束释放名额后再次补充，重新联网及下次进入前台也重试；不依赖后台续约。

设置页沿用现有布局显示“未来 7 天共 N 次，已安排 M 次”、最早未安排课程及原因。只有目标窗口全部有效课程都安排成功，才能显示覆盖完整；缺课表、缺频道、自定义时间不支持及超长课程分别列入未安排原因，不能通过从分母中排除来宣称全部成功。

#### 系统升级时的启动模式交接

从 iOS 18–25 升级至 iOS 26+ 后，不再上传远程计划并不等于旧计划已撤销。首次启用本地预约前，客户端须完成设备级启动模式交接；这也适用于仍可能保留远程注册状态的客户端切换。

1. 客户端持久化 `switchingToLocal` 及幂等交接 ID，停止旧远程同步任务，向服务端请求切换。交接与普通配置使用同一账号、设备身份和代次校验；总开关关闭时只清理，不创建预约。
2. 服务端在设备级锁/事务内将启动模式设为 local，递增模式代次，撤销 pending 和尚未进入 submitting 的 claimed 任务，并阻止旧同步请求重新启用远程模式。保留 submitting、submitted、submissionUnknown 及其课程身份和结束时间，返回交接凭据、模式代次和仍未结束的相关实例记录。交接请求重复执行返回同一已完成结果，不清空提交历史；不使用删除设备记录的方式完成交接。
3. 客户端收到并持久化成功结果后，先枚举系统活动：有效的 active/stale 接回保留，不重复预约；已结束的清理。已提交或结果不明且没有系统活动的当前实例按第 6 节前台恢复规则处理，不当作新的普通预约。其余未来课程才进入本地滚动预约。
4. 网络失败、响应丢失或交接中崩溃时，保留交接状态并用相同 ID 重试，设置页显示“等待完成启动方式切换”；确认成功前不新增本地预约。服务端已切换而客户端未收到结果时，也不能回退重建远程计划。正常保留仍有效的已有活动。
5. 交接不能撤回已在途的 APNs 请求。客户端持续按 `occurrenceId` 核对并清理迟到的重复活动；关闭总开关或退出账号后到达的结果不能恢复任何预约。前台恢复仍遵守第 6 节，不把历史提交记录变回 pending。

已有本地模式交接凭据且设备身份未变化时，无需每次打开 App 重新联网交接，可在有效缓存范围内预约。首次使用、没有远程注册历史的设备，由服务端确认本地模式；不能仅因本地缺少撤销凭据就假定服务端没有旧计划。

#### 预约额度不足时的近期优先规则

“保留已有预约”服从近期课程优先。按实际 `plannedStart` 从近到远排序，同刻按课程开始时间及稳定 `occurrenceId` 排序，保证每次核对结果稳定。只对当前账号、当前功能管理的 pending 预约执行替换，不结束 active/stale 来腾出名额。

- 有较近课程未安排时，先校验其快照、频道、有效期和时长，再正常尝试申请。仅在系统明确返回数量限额时，从已预约且排序更晚的课程中选择最晚一项让位；缺少频道等非额度错误不触发取消其他预约。
- 取消前持久化 `capacityRebalance` 原因并再次检查系统状态。若已转 active/stale 则保留，另找可替换项；确认取消完成后才重试申请较近课程。每次异步返回检查配置代次和总开关，过时代次不得继续取消或创建。
- 每次较近课程申请最多替换一项远期预约；取消后仍报限额则停止本轮新增，等待下一次核对，不继续批量撤销远期预约。若较近课程因其他原因失败，记录原因并尝试恢复被让位的预约一次，仍失败则保留缺口，避免循环申请。
- 被让位课程记为“未安排：名额优先用于近期课程”，不是用户移除或 terminal，仍计入 7 天目标数量；有名额释放、课表变化或下次进入前台时，按统一顺序重新补充。崩溃后根据账本和系统活动恢复核对，不把已取消项算作预约成功。
- 没有排序更晚的 pending 可让位时，保留现有活动并报告额度不足；不承诺一定能安排近期课程，也不切换为远程启动兜底。

### 4.3 每门课的实际启动时间

对实际课程实例按开始时间排序，使用完整相关课表计算前序课程结束时间，再筛选预约窗口，避免窗口边界漏掉仍在上课的前序课程。

```text
idealStart = course.start - leadMinutes × 60
previousEnd = 所有开始时间早于本课的课程的最晚结束时间（没有则不限制）
plannedStart = max(idealStart, previousEnd)
```

正常不重叠课表中，`previousEnd` 就是上一门课的结束时间。使用前序课程最晚结束时间可以避免异常重叠课表中漏掉尚未结束的更早课程。

- `plannedStart` 在未来：在该时刻预约或远程启动。
- `plannedStart <= now < course.end`：若没有对应活动且本次实例未结束，则按第 6 节核对是否允许首次启动或前台恢复；远程首次启动仍须检查提交记录。本地预约可使用 `now + 1 秒`，并再次确认仍早于课程结束。
- `plannedStart >= course.end` 或课程已经结束：不创建过期或没有有效展示时段的活动。
- 导入冲突按第 1 节逐节解决；调课或编辑再次产生冲突时，同样要求用户选择，不将冲突课程直接交给调度器。上述前序结束时间计算仍作为防御性约束。
- 已存在对应 active 活动时不再创建；尚未到上一门课结束时间时不能因为理想提醒时间已过而立即启动。
- 按 `course.end - plannedStart < 8 小时` 校验活动时长，包含提前提醒及课间；超过或等于 8 小时则不安排并显示原因，不静默截断、不拆成多个活动规避限制。用于限制后续启动的前序课程包含所有已选课程，即使该课程因不支持或申请失败而没有活动。

示例：提前量为 1 小时。

| 课表 | 实际行为 |
| --- | --- |
| 第 1–2 节、3–4 节 | 第 3 节的理想提醒落在上一门课内时，推迟到第 2 节下课启动；订阅第 4 节结束频道 |
| 第 1–2 节、7–8 节，间隔超过 1 小时 | 第 2 节下课收起；第 7 节上课前 1 小时启动；订阅第 8 节结束频道 |

时间比较只影响启动时刻，频道始终由本次课程最后节次决定。连堂课内部的小节不作为不同课程参与上述排序。当前活动结束依赖广播到达，即使启动计划不重叠，网络延迟仍可能造成短暂的显示重叠。

### 4.4 iOS 17

iOS 17 暂保留现有前台本地能力，不在本方案中增加逐活动 token 推送链路，也不承诺完整后台生命周期。技术上 iOS 17.2 起支持远程启动，但不支持频道广播；若未来完整支持，需另行设计逐活动更新与结束。

## 5. 客户端与服务端数据职责

客户端基于已经同步的课程安排展开实际日期，处理调休、调课。iOS 18–25 上传必要的远程启动计划；iOS 26+ 在本机生成 7 天预约，不上传远程启动任务，只获取作息和固定频道映射。服务端不需要课程名、教师或教室。

iOS 18–25 的同步结构如下；本次不兼容旧协议：

```json
{
  "protocolVersion": 2,
  "scheduleId": "main-campus",
  "scheduleVersion": "v3",
  "planRevision": 12,
  "coverageStart": "2026-09-22",
  "coverageEndExclusive": "2027-02-01",
  "leadMinutes": 15,
  "busyIntervals": [],
  "items": [
    {
      "occurrenceId": "opaque-stable-id",
      "supersedes": [],
      "dateKey": "2026-09-23",
      "startPeriod": 1,
      "endPeriod": 2
    }
  ]
}
```

设备注册另包含 push-to-start token、环境、Bundle ID 和不含账号明文的本机账号隔离标识，后者随远程启动写入 attributes。`endPeriod` 足以确定结束频道，但远程启动还需要日期及开始节次来计算启动时间。

服务端校验节次、日期范围、作息版本和设备身份，再计算时间并匹配频道。作息版本不一致时应要求同步，不能静默按不同版本解释节次。课程实例身份不能随提前量变化，用于去重、取消和更新。

自定义时间无法精确对应学校节次的课程，首版不提供自动实时活动，保留普通课表显示并明确标注未安排原因；不匹配“最近”频道、不创建缺乏可靠结束路径的预约。课表编辑、调休变化或学期切换后需重新同步，服务端不会自动获知尚未同步的本地变更。

不支持自动活动的已选课程仍占用真实上课时间。远程同步通过 `busyIntervals: [{startAt, endAt}]` 上传这些课程的绝对起止时间，不含课程文字、不产生启动任务，仅参与前序结束时间计算；服务端校验其日期范围、起止顺序以及与已选课程之间不存在实际时间冲突。本地使用相同占用区间规则，避免因跳过自定义课程而提前拉起下一门课。

### 5.1 稳定身份与计划版本

- `occurrenceId` 是账号内不含个人信息的不透明 ID，对应实际日期上的一个连续课程段。不能使用名称、列表顺序、提前量、频道或可变起止时间直接生成身份；导入的来源课程 ID、日期实例 ID 及分段 ID 需持久保存，重复导入相同数据复用身份。
- 修改名称、教室、提前量、计时模式及同一实例的节次边界保留身份。改到另一个实际日期属于新实例，原实例撤销。拆分或合并以 `supersedes` 保存并上传替代的原实例 ID；旧实例已有活动时，替代实例不能重复创建；自然结束或因第 6.2 节变更终止的实例也不能借替代关系重新启动。手动移除只抑制本次前台会话内的立即重建，下次打开 App 按第 6 节恢复，不永久禁止本次课程。服务端沿替代关系保留远程提交去重记录，前台恢复不清空这些记录。真正后续的独立课程实例不受影响。
- 作息版本描述学校时间；`planRevision` 描述单设备课程计划及设置，二者分离。服务端按设备接受单调递增版本，相同版本、相同内容幂等成功，相同版本不同内容或旧版本返回冲突；客户端先获取当前版本再基于最新快照重试。
- 同步为设备当前所需计划的完整快照，覆盖区间标明课表实际已加载范围，校验全部成功后原子替换。快照之外的旧未提交计划一并撤销，避免学期切换或覆盖范围缩短遗留旧任务；空列表撤销全部未提交计划。取消、已提交及终止身份单独保存，不因替换计划或 token 轮换而丢失。发送前再次核对设备状态、计划版本、实例状态、有效期及作息版本。
- 客户端上传已加载学期的完整有效日期范围，最多未来 370 天；服务端校验节次存在、同日实例互不重叠及身份唯一。单次实例与占用区间合计上限 10,000 项，超限整体拒绝且提示，不静默截断。iOS 26 不上传个人远程计划。

### 5.2 接口及缓存契约

- `GET /api/live-activities/broadcast-config`：返回协议版本、学校时区、作息标识/版本及节次表。iOS 26 的本地预约模式额外返回环境对应的最终节次频道映射和有效期；远程启动模式的常规计划同步不需要频道 ID；第 6 节前台恢复时可请求对应作息版本的有效频道映射。
- `PUT /api/live-activities/remote-start`：接收设备身份、token、环境、Bundle ID、计划版本及完整覆盖区间；返回已接受版本、同步截止日期、缺失频道/阻塞原因及设备撤销凭据。“计划已保存”与“频道齐全可发送”分别表示。
- `POST /api/live-activities/start-mode`：设备绑定的幂等模式交接接口，接收交接 ID、预期模式代次及目标 local 模式；原子阻止后续远程启动并返回交接凭据、模式代次及未结束实例的提交状态。远程计划同步须校验设备模式和代次，旧请求不得覆盖已完成的切换。
- `POST /api/live-activities/remote-start/revoke`：保留设备绑定的撤销能力，退出登录后仍可撤销原设备计划；不允许旧账号凭据撤销新账号设备。登出、关开关和异步注册返回采用同一代次校验，迟到注册成功必须追加撤销。
- 账号、APNs 环境、Bundle ID、作息标识和版本共同隔离缓存。token 轮换迁移设备身份及已提交记录，不能作为新设备重发当前课程；换账号清空个人快照和预约，撤销旧账号计划后同步新账号。
- 计划拒绝、频道缺失和离线重试均保留明确状态，设置已保存不等于计划已生效。系统权限被关闭时，前台核对取消本地预约并撤销远程计划；权限恢复后仅安排仍可启动且未终止的实例。

## 6. 用户修改提前量

每次修改提前量都先保存最新设置，再按系统版本重新配置，全部使用第 4.3 节的启动时间公式，不能仅修改 UI 中的设置值。

### iOS 26+

1. 保留已经 active 且仍有效的课程活动。
2. 取消现有尚未启动的课程预约。
3. 以当前时间重新展开未来 7 天课表，逐门重新计算启动时间与结束频道。
4. 按时间从近到远重新创建预约，检查申请结果并记录实际成功范围。
5. 连续快速修改时串行化重配并核对设置版本，停止旧任务继续创建，最终只保留最新设置对应的预约。

已有有效课表和频道缓存时可在本地重配，无需等待服务端修改个人启动计划。缺少必要元数据或系统拒绝预约时记录失败，不能把设置已保存当作预约全部成功。

### iOS 18–25

同步服务端更新设备设置，重算尚未启动的任务，并与任务领取、发送协调。发送前检查计划版本，已发送身份保持不变；已经提交给 APNs 的请求无法撤回。离线修改保存本地、联网后重试，同步前服务端仍执行旧设置。

### 共同规则

| 情况 | 处理 |
| --- | --- |
| 新的实际启动时间未到 | 改为新时间执行 |
| 理想提醒时间已过，但上一门课尚未结束 | 等上一门课结束后启动 |
| 实际启动时间已到，课程未结束且没有对应活动 | 按本节区分首次启动和前台恢复；总开关开启且实例有效时尽快启动，远程首次启动仍检查提交记录 |
| 该课程活动已经启动 | 保留现有活动，不关闭重建 |
| 课程已经结束或延后后没有有效展示时段 | 不再启动 |

修改提前量不改变下课频道和最终结束时间。默认提前量为 15 分钟。已有合法的 15/30/60 分钟值保持；其余 0–60 分钟值向上归入最近档位（0–15 → 15，16–30 → 30，31–60 → 60），缺失或非法值使用 15。该规则只处理本机保存的偏好，不要求兼容旧接口或旧活动。

### 用户移除活动与关闭总开关

- 用户手动移除活动不改变总开关，也不取消后续课程预约。当前前台会话内不因定时核对、修改提前量或重同步立即重建；下次打开 App（冷启动或从后台回到前台）时，只要总开关开启、系统权限允许、课程有效且 `plannedStart <= now < course.end`，就自动恢复。课程已结束则不恢复，尚未到实际启动时间则保留正常计划。
- 手动移除不是课程实例永久终止，不要求用户重新开关设置，也不需要确认。App 未运行期间移除、随后重开时同样恢复；先枚举并接回已有活动，避免重复创建。
- iOS 26+ 用本地创建或尽快预约恢复。iOS 18–25 的正常后台启动仍由服务端负责，但允许此次前台恢复在本机创建并订阅对应结束频道，无需服务端重发同一启动；缺少有效快照或频道时先加载，失败显示原因并保留恢复需求。iOS 17 继续使用现有前台本地能力。
- 服务端保留已提交及结果不明的实例记录，不因前台恢复重置为 pending。远程路径恢复前须协调撤销本次尚未提交的远程任务；已在途的请求无法撤回，客户端按 `occurrenceId` 接回并清理迟到的重复活动。通过设备绑定、带计划版本校验的前台恢复接口原子撤销本实例未提交任务并标记由本机接管，返回有效频道映射和提交状态；同一恢复请求幂等，后续完整计划同步不得重新生成该实例的远程任务。离线且不能确认已接管或已提交时保留恢复需求，联网后重试。恢复活动继续订阅原本正确的结束频道，不增加逐活动结束推送。
- 用户关闭设置总开关时，先持久化关闭状态，再结束当前活动、取消全部未启动的本地预约，并撤销服务端后续启动计划。离线撤销持久化重试；服务端收到撤销前及已经提交的在途请求仍可能到达，客户端发现后清理。总开关关闭期间，冷启动、回前台、同步、重试及迟到异步结果均不能恢复活动或预约。
- 只有用户主动重新开启总开关才恢复安排：当前仍有效课程按启动时间规则恢复，未来课程重新安排，已结束课程不恢复。

### 6.1 本地预约账本与恢复

账本以账号、设备及 `occurrenceId` 为键，至少记录 `requesting / pending / active / dismissed / missing / terminal / retryableFailure`、Activity ID、配置代次、计划启动时间、前台会话代次及取消原因。`dismissed` 表示手动移除、下次打开 App 可恢复；`missing` 表示系统无对应活动且原因未知；`terminal` 仅用于课程自然结束或第 6.2 节要求本次不再重建的变更。关闭总开关由持久化设置阻止创建，不把所有未来课程永久标为 terminal。

调用系统申请前持久化 requesting，成功后保存 Activity ID。崩溃恢复先枚举系统活动并按身份接回，再决定是否恢复。每次冷启动或从后台进入前台生成新的前台会话代次；普通定时核对及设置同步不产生新会话。恢复流程串行执行，每次异步返回后检查总开关、账号和配置代次，过时任务创建出的活动须清理。

核对前优先检查总开关及课程有效性；总开关关闭或本次已 terminal 时，清理迟到活动。配置重建、关闭功能或退出账号主动取消的 pending 必须在调用取消前记录原因，不能把相应的 ended 回调误判为用户移除。其余核对规则如下：

| 账本与系统状态 | 处理 |
| --- | --- |
| 系统存在对应 pending | 接回账本；配置未变则保留 |
| 系统存在 active 或 stale | 按已启动处理，不重复创建；过期则结束 |
| 观察到用户 dismissed，课程仍有效 | 记为 dismissed，本会话不立即重建，下次打开 App 恢复 |
| 观察到 ended | 根据课程是否结束及主动取消原因分类；无法判断时记为 missing，不永久阻止前台恢复 |
| 已确认成功预约，但启动时间已过且系统无此活动 | 记为 missing；打开 App 时按有效性恢复，不等待证明是否为用户移除 |
| requesting 后崩溃，系统无活动且启动时间已过 | 重开 App 时核对后恢复，不因结果未知永久跳过本次课程 |
| 启动时间未到、系统无活动 | 总开关开启且课程有效时可重新预约；显式申请失败按原因重试 |
| 因修改配置主动取消 pending | 记录重配原因，允许同身份按新配置重建 |

系统活动列表缺失不能证明用户移除，也可能是系统未启动；前台恢复统一按当前课程、总开关及已有活动判断。用户本会话内再次移除后，须等下一次打开 App，不能被后台轮询立即恢复。终止及提交记录保留至所属学期结束且实例时间已经过去，前台恢复不清空远程提交去重记录。取消前再次检查状态，若 pending 已转 active，则按当前活动规则处理，不能把它误记为可重建的预约。

### 6.2 已启动课程及作息变更

| 变更 | 未启动计划 | 已启动活动 |
| --- | --- | --- |
| 名称、教师、教室或计时模式 | 更新快照，无需改频道 | 更新快照和显示内容，保留活动 |
| 提前量 | 按本节重配 | 保留活动 |
| 课程起止、小节选择、结束节次或作息版本 | 撤销旧计划，按新数据重建 | 客户端获知后结束本次活动，记为 terminal，本次不重建；后续课程按新数据安排 |
| 删除课程或出现待解决冲突 | 撤销受影响计划 | 结束受影响活动并记为 terminal |

首版不尝试在已经启动的活动上切换频道，也不为改结束节次追加一次远程启动。用户手动移除按第 6 节在下次打开 App 恢复，不属于此处的 terminal；本表的课程变更终止仍独立处理。App 未运行或未同步时无法按个人变更立即结束，旧活动仍按原版本频道结束；服务端不能为单人的调课向整个频道提前发 `end`。客户端下次核对清理这些旧活动。

## 7. 服务端调度与万人规模

仅 iOS 18–25 需要逐设备启动，iOS 26+ 使用本地预约；两者都按频道更新和结束。假设 1 万名活跃用户全部使用远程启动路径、每人每天 5 次课程活动，远程启动约为每天 5 万次请求；更新和结束请求数主要随频道及作息边界增长，而非随人数增长。

主要风险是万人同时进入提醒窗口的峰值。若实测发送吞吐为 2,000 条/秒，提交 1 万条请求理论上需约 5 秒，这不是 APNs 的速率承诺，也不包含设备送达延迟。

实现建议：

- 使用到期时间索引，仅领取到期任务，不逐秒遍历全部用户和课表。
- 批量领取、使用领取租约或锁协调多实例，处理服务中断后的任务恢复。
- 复用 HTTP/2 连接和 APNs 签名，限制并发，按真实峰值压测调整 worker 容量。
- 保存已同步的完整学期计划，只物化未来 48 小时启动时间范围内的任务；每分钟及每次计划同步后补充，以设备、实例身份唯一键去重。服务重启先补齐窗口，刚过期望启动时间但仍处于有效期的任务可执行；不能因滚动窗口要求用户每天打开 App。
- 重试前核对任务版本和有效期，过期启动不积压补发；临时失败退避，失效 token 停用并等待重新注册。
- 记录计划到发送延迟、APNs 接受/拒绝、错误原因和重试次数，不把 APNs 成功标为设备已送达。
- 端到端不能承诺 exactly-once；按下述规则处理网络中断及发送后落库前崩溃，不因租约过期就盲目重复提交启动。

允许启动、阶段更新和结束存在少量时间差，保留现有默认约 5 秒的调度检查间隔，不设置“计划时间后 2 秒内提交 APNs”的目标，也不要求为此改成精确定时唤醒。

检查间隔是服务端查看到期任务的间隔，不是手机倒计时的刷新间隔。总延迟还包含任务排队、请求提交及 APNs 送达，5 秒不是端到端延迟上限；iOS 26 已预约活动的本地启动不受服务端检查间隔影响。项目现有每批 200 项、最多 12 路并发不能直接当作万人同时启动的容量证明，仍需通过峰值压测确认不会持续积压或导致任务过期。

### 7.1 远程启动有效期与发送状态

正常计划的 `expiresAt = min(course.end, max(course.start + 60 秒, plannedStart + 5 分钟))`。用户首次同步或修改配置时，如果实际启动时间已过、课程仍有效且本次从未提交启动，则生成一次补启动，有效期取 `min(course.end, 本次接受计划时间 + 5 分钟)`；相同版本重试不能不断延长有效期。服务中断后的恢复不属于用户重新配置，不能借恢复重置过期时间。

提交 APNs 时使用当前实际发送时间作为启动 `timestamp`，设置 `apns-expiration: 0`，避免离线存储后很晚才启动。服务器重试期限与 APNs 存储期限分别控制；发送前必须再次判断未到最终结束时间。先保存如下状态再进行外部发送：

| 状态/结果 | 后续行为 |
| --- | --- |
| pending，尚未提交 | 有效期内领取；配置改变可撤销或更新 |
| claimed，尚未进入发送阶段 | 租约到期可重新领取，重新验证计划版本 |
| submitting，已持久化发送意图 | 进入可能已提交阶段，其他 worker 不再发送同实例 |
| APNs 明确接受 | 记为 submitted，保留本次身份至学期结束 |
| APNs 明确临时拒绝，或可证实请求尚未发出 | 有效期内退避重试，重试前重新验证版本 |
| 超时/断连无法确认是否接受，或 submitting 后进程崩溃 | 记为 submissionUnknown，不自动重发本次；下一门课照常 |
| token 失效、永久拒绝或任务过期 | 停用 token 或终止该任务，记录明确原因 |

`submissionUnknown` 不标为成功送达，也不通过修改提前量、token 轮换或重新同步变回 pending。该策略优先避免重复启动，允许少数结果不明的启动被跳过。提交前的版本检查与进入 submitting 状态在设备级锁/事务内完成；配置更新不能撤回已经进入提交阶段的请求，但必须撤销其他尚未提交的旧任务。关闭功能及退出账号同样遵守这一界限。

广播任务与逐设备启动使用各自受限的执行队列，避免万人启动积压阻塞公共结束广播；检查节奏仍沿用现有配置。压测记录启动与广播各自的排队时间、提交延迟分位数、过期数量及重试量，不能只统计每天总请求数。

## 8. 固定频道跨日复用决策

按用户确定的方案，同一最终节次跨日共用固定频道，7 天预约可指定相同频道。不按日期隔离，也不将 pending 预约是否受之前的 `end` 影响作为实施前置验证项。

频道生命周期独立于活动、活动结束不删除频道，有官方文档依据。至于 pending 预约与 `end` 的交互，本方案按不影响未来预约的设计假设执行，不将该假设表述为 Apple 已明确保证的行为。本轮不再展开该问题或因此阻塞方案。

## 9. 实现边界与验收

需要调整的现有部分：

- 本次更新不考虑旧版兼容，客户端和服务端配套切换，不要求旧接口、旧频道协议继续服务旧客户端。新版自身的作息变更、已启动活动结束节次变更按第 3.2、6.2 节处理。
- 启动计划从“每个学校课节块一次”改为“每次课程一次”。
- 结束频道从学校大时段改为课程最终下课节次。
- 统一分节/整堂时间线，保留现有 UI 视觉设计。
- 设置变化、计划撤销、token 轮换、换账号和前台恢复继续维持一致性。
- iOS 26+ 固定采用未来 7 天本地预约，iOS 18–25 采用远程启动，避免重复启动。
- 所有计划按上一门课结束时间修正启动时刻；每次调整提前量都重新配置未启动计划。

### 9.1 实现顺序

1. 实现逐节冲突选择及持久课程身份，再实现共享的日期展开、连续段划分和时间线解析；客户端与服务端以共同测试样例验证启动时间计算。
2. 实现新版作息/频道契约、广播事件及版本保留，完成服务端计划替换、发送状态和撤销逻辑。
3. 实现 App Group 快照及预约账本，接入 iOS 26 滚动核对和 iOS 18–25 计划同步，再接入设置与已有视觉组件。
4. 执行故障恢复及真机验收；文档中的目标不得仅以内存 ActivityKit 替身通过来判定实现完成。

### 9.2 验收矩阵

| 场景 | 必须满足的结果 |
| --- | --- |
| A 1–3 / B 2–4 冲突，逐节选择 | 实际每节只保留一门课，按选择结果形成连续段及正确结束频道 |
| A 1–3 中第 2 节改选 B | A1、B2、A3 为三个活动实例；不能让 A 跨过 B 合并 |
| 相同课表反复导入、编辑名称、修改提前量 | 身份不变，不重复启动，不丢失终止记录 |
| 三档提前量 × 分节/整堂模式 | 课前、上课、课间、最终结束均按时间线表解析，边界不多算一节 |
| 第 1–2 / 3–4 节及第 1–2 / 7–8 节 | 前者提醒不进入上一门课；后者在长间隔内正常独立启动 |
| 无课日、调休、周末补课、手机更换时区 | 按学校日期展开；有效课程有广播，手机时区不改变实际启动时间 |
| 手动移除后重开 App、改设置或同步 | 当前会话不立即重建；下次冷启动或回前台恢复仍有效课程，已结束课程不恢复；覆盖 App 未运行期间移除及 iOS 18 前台频道恢复 |
| 关闭总开关、离线关闭、退出期间注册迟到 | 结束活动并取消全部预约，远程撤销可重试；重开 App 或迟到结果不恢复；用户主动开启后才重新安排 |
| 冷启动/回前台滚动、连续快速改提前量 | 仅最新代次可创建，未变预约除额度让位外保留，active/stale 不被当作缺失 |
| 7 天窗口数量限额、中途某门申请失败 | 按近到远申请，显示实际数量及最早缺失，释放名额后前台补充 |
| iOS 18 升级到 iOS 26，远程仍有整学期计划 | 交接成功后才新增本地预约；旧同步不能恢复远程任务，已有活动接回，提交历史保留 |
| 交接离线、响应丢失、崩溃、旧请求迟到 | 幂等重试并显示等待状态；未确认前不新增本地预约，总开关关闭时不恢复 |
| 交接时存在 submitting/submitted/submissionUnknown | 不作为全新预约重复安排，缺失活动走前台恢复；迟到活动按身份去重 |
| 名额被远期课程占满，新增今天的课程 | 额度拒绝后让最晚 pending 腾位，近期课程优先；远期仍列为未安排，active/stale 不受影响 |
| 腾位时 pending 转 active、取消后仍满、重配中崩溃 | 不结束已启动活动，不连续清空远期预约；按持久化原因和系统状态恢复，成功数量真实 |
| 近期课程缺频道或替换后申请失败 | 缺频道不触发腾位；替换后非额度失败尝试恢复被让位预约，失败均保留明确原因 |
| 旧映射离线、作息升级、频道创建失败 | 缓存不能无限续期，新旧版本不混用，已承诺广播不提前停止 |
| 预约前后崩溃、pending 在重配时转 active | 能接回既有活动，不重复申请，不把已启动当作取消后可重建 |
| 本次活动进行中修改结束节次或删除课程 | 前台结束本次、不重建，不影响频道内其他学生；后续计划更新 |
| 广播迟到、乱序、漏收、断网重连 | 按实际时间恢复阶段；结束后不补旧更新，不承诺离线准点收起 |
| 峰值启动与公共结束同刻 | 结束队列不被启动队列阻塞，无持续积压，统计过期和提交延迟 |
| APNs 临时拒绝、token 失效、发送后崩溃 | 明确拒绝可受控重试；结果不明不自动重发，后续课程仍可执行 |
| 空计划、旧版本同步、token 轮换及换账号 | 完整替换范围正确，旧版本不覆盖新计划，身份与隐私隔离不丢失 |
| 自定义时间、超长课程、快照缺失 | 明确未安排/不可用原因，不使用错误频道或其他课程信息 |

自动检查覆盖时间线解析、身份稳定性、计划版本、租约恢复及载荷 schema；沿用现有服务端测试与 `ios_next/scripts/check-live-activity.sh` 并扩展上述场景。真实 SDK 编译检查预约接口和共享模型；iOS 18 与 iOS 26 真机分别在开发签名及 TestFlight 环境验收启动、手动移除、锁屏阶段更新和结束。第 8 节约定的频道复用假设保持不变，不将其重新设为实现前置门槛。

本草案不包含提交、推送或生产部署授权。后续生产推送与部署遵循仓库的 [production-requirements.md](production-requirements.md)。
