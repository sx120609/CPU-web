# CPU-web 生产推送要求

## 适用范围

本要求适用于 `main` 的每一次推送，包括仅修改文档或工作流的推送。生产部署是独立操作；完成推送和 GitHub 编译不代表获得了部署授权。

## 构建来源

1. GitHub Actions 是正式生产制品的唯一权威构建来源。
2. 本地测试、类型检查和构建可以按改动风险执行，但不是固定的推送前完整构建门禁，生成物也不得当作正式生产制品或推送完成证据。
3. 生产部署应使用绑定精确提交 SHA、经过清单和 SHA-256 校验的 GitHub 制品，不把开发机或生产服务器本地编译作为常规生产路径。

## 推送与 GitHub 门禁

1. 只暂存本次任务文件，保留工作区中不相关的用户文件和生成物。
2. 完成并推送最终提交，记录本地完整提交 SHA，并验证本地 `HEAD` 与远端 `main` 一致。
3. `main` 的每次推送都会触发 `Linux deployment artifact` 工作流。必须核对该工作流：

   - 检出的是本次推送的完整提交 SHA；
   - 在 Ubuntu 24.04、Node.js 24 环境中成功构建 Server、Web 和 VoiceHub；
   - 成功生成、校验并上传名称中含完整提交 SHA 的 Linux 制品。

4. 只有远端提交一致、精确 SHA 的 GitHub 工作流成功且制品存在，才可以报告“推送及编译完成”。
5. CI 仍在运行、失败、被取消、没有对应 SHA 的运行记录或没有制品时，必须明确报告未完成。`git push` 成功、本地构建成功或其他 SHA 的 CI 成功都不能替代本次 GitHub 构建。

## 部署边界

上述流程只负责提交、推送、GitHub 编译和制品验证。除非用户明确要求部署，否则不得执行 `deploy.sh update`、后台更新部署或任何生产发布操作。正式生产发布应使用 `DEPLOY_BUILD_MODE=ci`，在精确 SHA 的 GitHub 制品缺失时失败关闭，避免回退到生产机编译。
